## 1. 结论先行

影织 AI 的可信创新不应表述为“有七个 Agent”“能用大模型剪视频”或“使用了 LangGraph、pgvector、Flutter”。这些属于职责划分、工程集成或可替换实现，单独不能证明创新。

本项目最值得投入并且能够被对照验证的核心是 **创作约束闭环**：

1. **证据驱动的故事覆盖闭环**：把用户表达目标拆成故事节点，用真实素材区间、转写和关键帧作为证据；将结果区分为 `covered / insufficient / uncertain / missing`；对可执行的缺口生成补拍卡、替代、重构或略过路径；新素材经重新分析后回写节点状态。
2. **依赖感知的局部重规划闭环**：将“只换开头、保留采访和结尾”解析为作用范围和约束，沿故事节点、时间轴、字幕、声音和转场依赖传播影响；锁定内容不可暗改；先产出差异草案，再由用户确认并生成不可变新版本。
3. **受约束协作作为可靠性支撑**：七类角色使用统一输入输出、证据引用、预算、状态、审批和恢复机制。它的价值在于让前两个闭环可追溯、可暂停和可恢复，而不是角色数量本身。

**重要性判断**：第 1 项解决“故事是否有真实素材支撑”，第 2 项解决“修改是否可控”，两者分别对应创作前的可行性和创作后的可逆性；首轮原型应优先验证“缺口→补拍→覆盖更新”和“锁定→局部修改→差异确认”两个闭环。摄影实时提示、跨模态检索、声音设计和七角色完整协作仍须保留，但应作为闭环的输入或扩展，而不是抢占核心机制验证资源。

## 2. 方案与现有能力的边界

### 2.1 能力分层

| 能力 | 判断 | 不能单独作为创新的原因 | 本项目的可验证增量 |
| --- | --- | --- | --- |
| 七个专业 Agent | 常规编排/产品表达 | 角色命名和模型实例数不等于协作效果 | 角色边界、证据引用、状态流转、冲突恢复在同一创作任务中的可观察收益 |
| 多模态分析与语义检索 | 成熟方向的工程应用 | 关键帧、转写、向量检索本身已有通用实现 | 将片段证据绑定到故事节点、缺口判定和版本决策，而不是只返回搜索结果 |
| 文本/语音生成故事板 | 常见生成式功能 | “生成大纲”不保证真实素材可执行 | 每一节点都有候选区间、支持状态、时间预算和用户处置 |
| 对话式改片、多轨编辑 | 常见产品能力 | 自然语言改片和多轨时间轴本身不构成独占创新 | 影响集合、锁定保护、依赖传播、差异预览及版本确认 |
| 实时构图/曝光/稳定提示 | 端侧 AI 应用 | 视觉提示属于成熟应用方向，且真机性能有风险 | 把当前拍摄任务与故事缺口绑定，并把采集结果回写故事覆盖 |
| LangGraph、队列、Outbox、不可变版本 | 工程可靠性 | 是实现手段，不是业务创新 | 为创新闭环提供可恢复、可审计、不可静默改历史的执行基础 |

对外比较时只使用“官方公开能力/常见工作流”作为能力类别，不宣称其他产品缺少某项功能，也不宣称本项目首创。最终结论必须来自同一素材、同一模型预算、同一任务集上的实验。

### 2.2 方案版本冲突与统一口径

执行材料存在两个资源口径：需求基线和仓库路线图为 **三人、2026-11-15 至 2027-01-13（含首尾共 60 个日历日）**；项目计划第 3.1/3.2 节及可行性材料的进度/工作量估算使用 **四人、24 周、每人每周约 16 小时，合计 1,536 人时**。两个周期和人力假设不能混用。若三人仍按每周 16 小时，60 日约提供 411 人时，仅约为另一方案预算的 27%；该算式是资源敏感性估计，不是团队真实工时。

本次保持需求基线、日期和完整范围，路线图标注为风险优先的执行建议；不认定 60 日内全量交付已经可行，也不擅自将 24 周批准为新工期。启动时须核定实际工时、技能、设备和集成依赖，再决定增援、延长周期或提出正式需求变更。不能仅靠调整章节顺序解决资源缺口。

两份材料的共同优先级应统一为：先建立契约和确定性校验，再完成证据覆盖与缺口闭环，再完成局部重规划，最后扩展实时摄影、七角色全链路、声音和审片。完整七模块、七角色、双端和五场景不删除，只调整证明顺序。

## 3. 创新重要性、风险与证据强度

| 机制 | 用户/评审重要性 | 实现风险 | 当前证据强度 | 必须回答的问题 |
| --- | ---: | ---: | ---: | --- |
| 证据→覆盖→缺口→补拍→回写 | 高 | 高 | 计划性 | 缺口是否是真缺口？补拍是否能改变状态？是否减少无效沟通或返工？ |
| 影响集合→锁定保护→局部重规划 | 高 | 高 | 计划性 | 非目标内容是否不变？锁定违规是否为零？局部修改是否比全片重算快？ |
| 结构化七角色协作 | 中 | 中 | 计划性 | 与单角色/基础自动剪辑相比，质量、失败率或成本是否改善？ |
| 实时摄影提示 | 中 | 高（设备） | 计划性 | 本地提示是否满足 500ms 目标，且采集素材真能补足节点？ |
| 事件检索与声音/审片扩展 | 中 | 中 | 计划性 | 是否改善定位和修复，而非只增加功能项？ |

当前不应使用“显著提升”“行业领先”“首次”等结论。若消融或盲评未显示收益，应缩小创新表述，保留真实工程价值。

## 4. 怎样证明创新成立

实验应拆为两条轴，避免“七角色 + 更多调用 + 更多功能”的混合比较。完整协议和分母定义见 [评测与证据协议](evaluation.md)。

| 对比 | 控制条件 | 回答的问题 |
| --- | --- | --- |
| 人工工作流 vs 完整系统 | 同素材、任务、输出规范；工具熟悉度与练习记录 | 用户操作、查找缺口与返工成本是否改善 |
| 基础自动方案 vs 增加证据闭环 | 同模型、同角色布局、同信息与预算上限 | 缺口判定和补拍决策是否更有效 |
| 全片规划 vs 依赖局部规划 | 同输入版本、同锁定规则和校验器、同质量门槛 | 非目标保护、重算规模、规划时延和费用是否改善 |
| 单规划角色 vs 七职责协作 | 两侧均启用相同机制、工具、门控和预算上限 | 分工本身是否带来质量、恢复或成本收益 |

来源约束、缺口、任务排序、依赖传播分别消融。去除锁定检查仅用于隔离的故障样例回放，测量违规拦截，不能作为可发布系统或对真实项目禁用校验。对缺少补拍指导的方案提供相同可用补充素材池，另做用户实际拍摄试验，避免给完整方案额外证据而误归因于算法。

目标沿用来源中的缺口精确率 ≥ 0.80、召回率 ≥ 0.75、处理后覆盖率 ≥ 0.90；锁定保护 100%、影响集合外规范化变化率 0。以上均未实测。低覆盖、超预算、放弃、等待与失败必须进入结果记录；只能在开发集上调整权重，不能根据测试结果反改分母或阈值。


## 5. 重构后的执行顺序

### 阶段 0：契约与最小可验证内核

冻结故事节点、证据引用、覆盖状态、补拍任务、影响集合、锁定摘要、EditDraft 和 Version 的 Schema；先实现纯函数校验和固定样例，不接真实模型也能运行机制测试。

### 阶段 1：证据闭环

完成素材区间、转写/关键帧引用、节点候选、缺口分类、补拍卡、替代/重构/略过决策和新素材验证。首个演示必须能说明“为什么缺、拍什么、拍回后什么改变”。

### 阶段 2：局部修改闭环

完成自然语言修改的结构化目标、依赖图、影响集合、锁定冲突、差异预览、确认和不可变版本。先支持不改时长的开场替换，再逐步增加声音、字幕、转场和全局时长传播。

### 阶段 3：协作和扩展能力

把导演、编剧、视觉、摄影、剪辑、声音、审片接入上述两个闭环；增加中断恢复、预算、权限、Outbox 和故障注入。七角色完成以“有输入/输出/证据/验收日志”为准，不以页面或角色名为准。

### 阶段 4：双端和五场景交付

Web 提供完整确认与差异界面，Flutter 提供摄影和补拍采集；再覆盖校园、旅行、家庭朋友、个人 Vlog、小型组织宣传五类场景。性能目标、实时摄影和导出在真实设备/配置下分别测量。

## 6. 文档重构规则

- 需求基线 `docs/requirements.md` 保持原文和哈希，不把新判断写回基线。
- 详细设计以“机制 → 契约 → 服务 → 页面 → 验证”组织，所有核心流程回链本文。
- Agent 设计以两个核心闭环的角色输入输出和门控点组织，七角色保留但不再作为创新证据。
- 数据库设计明确保存“证据、覆盖判定、补拍结果、影响集合、锁定摘要、差异和实验记录”所需事实；不为堆表而增加业务表。
- 路线图以风险优先和可证伪里程碑排列；未实现、未测试、未实测继续明确标注。
